An App's screens are React components placed in `screens/*.tsx`. Each file becomes one named screen — `screens/inbox.tsx` becomes the `inbox` screen. Screens are compiled by `@grasp-os/compiler` into ES modules with CSS and served as static assets; the browser loads them inside sandboxed iframes so that no screen code can reach the host page or make direct network calls. All communication goes through a structured bridge to core, which checks the person's session and role on every single call.

## Compilation and the `@grasp-os/ui` component library

Screens are compiled by `@grasp-os/compiler` into plain ES modules and a CSS bundle. The compiler resolves two special imports:

- `@grasp-os/sdk/screen` — the only way to reach the server or workflows (see below)
- `@grasp-os/ui` — the App's component library: shadcn components built on Base UI, styled with Tailwind v4

Use `@grasp-os/ui` components as you would any shadcn component. Because styles are inlined at compile time, no external stylesheet is needed:

```tsx
import { Button } from "@grasp-os/ui/button";
import { Card, CardContent, CardHeader, CardTitle } from "@grasp-os/ui/card";
```

<Note>
Screens have **no access to the network**. Any `fetch`, `XMLHttpRequest`, or WebSocket call from screen code is blocked by the iframe sandbox. All data must come from the App's server via the SDK.
</Note>

## Calling the server: `callServer`

`callServer` makes a one-shot call to a named method of the App's server, forwarding `args` and returning the method's answer. Core checks the session on every call.

```ts
import { callServer } from "@grasp-os/sdk/screen";

// Calls App.addNote(_caller, note) on the server
await callServer("addNote", "Follow up with Acme");

// With a typed return value
const notes = await callServer<string[]>("notes");
```

`callServer` rejects when the server refuses or fails. The rejection's `code` property identifies the reason — `app.failed` means the server method itself threw; other codes come from core's own checks (role, version, timeout, and so on).

## Live subscriptions: `useLive`

`useLive` subscribes to a server method that accepts a Watcher callback. It returns the latest value as React state, starting with `initial` and updating whenever the server calls its callback. The subscription is re-established automatically when the connection drops.

```ts
useLive<Value>(method: string, initial: Value, ...args: unknown[]): Value
```

Whenever `args` change (compared by JSON serialisation), `useLive` tears down the old subscription and starts a new one. This means you can safely pass a record ID as an argument to subscribe to that record's updates:

```tsx
import { Button } from "@grasp-os/ui/button";
import { callServer, useLive } from "@grasp-os/sdk/screen";

export default function Notes() {
  const notes = useLive<string[]>("watchNotes", []);

  return (
    <div>
      <ul>
        {notes.map((note, i) => <li key={i}>{note}</li>)}
      </ul>
      <Button onClick={() => void callServer("addNote", "New note")}>
        Add note
      </Button>
    </div>
  );
}
```

The server-side counterpart must hold the callback via `onChange.dup()` and call it whenever the data changes. See [App Server — The Watcher pattern](/apps/server#the-watcher-pattern-for-live-updates) for the full server implementation.

## Workflow integration: `useWorkflow`

`useWorkflow` gives a component everything it needs to interact with one of the App's workflows — current runs, starting new ones, reading status, and answering decisions.

```ts
const intake = useWorkflow(workflow: string): {
  runs: ScreenRun[];
  start: (input?: unknown) => Promise<WorkflowRun>;
  status: (run: string) => Promise<ScreenRun>;
  decide: (run: string, decision: string, answer: DecisionAnswer) => Promise<void>;
}
```

`runs` is the live list of the workflow's runs, newest first (up to 100), kept up to date as runs start, progress, and end. `start` begins a new run; `decide` answers an open decision that the person is allowed to answer.

```tsx
import { Button } from "@grasp-os/ui/button";
import { useWorkflow } from "@grasp-os/sdk/screen";

export default function IntakePanel() {
  const intake = useWorkflow("invoice-intake");

  return (
    <div>
      <Button onClick={() => void intake.start({ invoice: "INV-007" })}>
        Start intake
      </Button>
      {intake.runs.map((run) =>
        run.waitingFor.map((decision) => (
          <Button
            key={decision.name}
            onClick={() =>
              void intake.decide(run.id, decision.name, { approved: true })
            }
          >
            Approve — {decision.description}
          </Button>
        ))
      )}
    </div>
  );
}
```

## Following a single run: `useRun`

`useRun` follows one run by its ID, however old it is. Unlike `useWorkflow`, which lists only the newest 100 runs, `useRun` retrieves any run by ID. It returns `undefined` while the first read is in flight, and `null` when core has no such run or the person may not see it.

```ts
const run = useRun(workflow: string, run: string): ScreenRun | null | undefined
```

```tsx
import { useRun } from "@grasp-os/sdk/screen";

export default function RunDetail({ id }: { id: string }) {
  const run = useRun("invoice-intake", id);

  if (run === undefined) return <p>Loading…</p>;
  if (run === null) return <p>Run not found.</p>;

  return (
    <p>
      {run.status} — started {run.createdAt}
    </p>
  );
}
```

## Imperative equivalents: `followRuns` and `followRun`

For cases outside React components, the same subscriptions are available as imperative functions that take a callback and return a stop function:

```ts
// Follows all runs of a workflow
const stop = followRuns("invoice-intake", (runs: ScreenRun[]) => {
  console.log("Runs updated:", runs.length);
});

// Follows one run by ID
const stopOne = followRun("invoice-intake", runId, (run: ScreenRun | null) => {
  console.log("Run updated:", run?.status);
});

// Stop following
stop();
stopOne();
```

Both back off up to 30 seconds on connection drops and resume automatically.

## Key types

### `ScreenRun`

A `ScreenRun` extends `WorkflowRun` with live decision data:

<ParamField path="id" type="string">
  The run's unique ID.
</ParamField>
<ParamField path="workflow" type="string">
  The workflow ID (`invoice-intake`, for example).
</ParamField>
<ParamField path="version" type="number">
  The App version the run executes.
</ParamField>
<ParamField path="status" type='"running" | "waiting" | "paused" | "completed" | "failed" | "cancelled"'>
  Where the run is right now.
</ParamField>
<ParamField path="waitingFor" type="WaitingDecision[]">
  The decisions the run is blocked on; empty once it has ended.
</ParamField>
<ParamField path="startedBy" type='{ type: "person"; userId: string } | { type: "trigger" }'>
  Whether a person started it (and acts for them) or a trigger did.
</ParamField>
<ParamField path="createdAt" type="string">
  ISO 8601 timestamp.
</ParamField>
<ParamField path="endedAt" type="string | null">
  ISO 8601 timestamp, or null if still running.
</ParamField>

### `WaitingDecision`

<ParamField path="name" type="string">
  The decision's name as declared in the workflow — what `decide` takes.
</ParamField>
<ParamField path="description" type="string | undefined">
  Human-readable description from the workflow's `step.decision` options; only shown to the run's starter, admins, and whoever may answer.
</ParamField>
<ParamField path="expiresAt" type="string">
  ISO 8601 deadline — no answer counts after this.
</ParamField>

### `DecisionAnswer`

<ParamField path="approved" type="boolean" required>
  Whether the decision was approved.
</ParamField>
<ParamField path="payload" type="Json | undefined">
  Extra data the workflow asked for, such as `{ comment: "See note" }`; at most 4 KiB.
</ParamField>
